| ID | Question | Why it matters | Proposed default (unconfirmed) |
|---|---|---|---|
| O1 | **How does the CROIP -> iDARMS sync actually arrive?** CROIP publishes to exchange `croip.domain.v1`, but no per-concession queue, binding, credential or filter exists in its code. Will iDARMS connect to a CROIP-hosted broker, or does CROIP forward to an iDARMS endpoint? Who provisions and secures the queue? | Replica ingestion cannot be finished without it. | Build the consumer behind a `CroipSyncSource` interface. Test with a local RabbitMQ fixture. |
| O2 | How is concession scope derived for synced events? CROIP's ratepayer event carries a zero-UUID concession and a possibly-null assembly. Can a ratepayer belong to several concessions? | Wrong scope leaks other concessions' people and properties. | Scope by `assemblyId` against our assigned assemblies from `GET /v1/assemblies`. Drop anything else. |
| O3 | Which ratepayer/property fields may a concessionaire store? CROIP's sync event currently includes phone and email. | Framework §8 requires an approved field-level sharing schedule. | Store only identifiers, assembly, property class/use and status. Contact data only as needed for messaging. |
| O4 | Does CROIP emit update events (`ratepayer.updated`, `property.updated`)? None found in its outbox calls. | Without them the replica goes stale. | Add a periodic reconcile read once an API exists. Do not poll blindly. |
| O5 | May iDARMS bill a property whose CROIP verification status is not yet verified? | Defines the billing guard. | Bill only verified properties. |
| O6 | Registration while CROIP is unreachable, and read-your-writes. Framework says a central outage must not stop local collection, but registration now depends on CROIP. | Offline agents and UX. | Queue with idempotency key, show "syncing", block billing until a CROIP ID exists. |
| O7 | **Which channel carries our bills and payments to CROIP?** CROIP's billing REST intake (`POST /v1/bills`, `/v1/bills/{n}/payments`, decimal amounts, `externalBillRef`, `clientEventId`) is what its Postman, portal and README use. The Framework's event gateway (`/v1/events`) accepts events but CROIP says bills and payments do not use it, and nothing consumes them. Does CROIP converge on one channel? Which events does the reconciliation engine actually read? | Wrong choice means rebuilding the reporting pipeline. | Contain it in the adapter. Stub both. Treat REST (6a) as the working channel today and the gateway (6b) as the target. Never write business services against either directly. |
| O8 | Published event schemas and code lists (authority, jurisdiction, revenue codes, event type names). | Contract tests need fixed schemas. | Use Framework §5 names. Fetch codes from `/v1/reference-data`. |
| O9 | Provider/PSP integration: who confirms payments (iDARMS-side callbacks) and how that relates to CROIP's independent evidence feeds. | Distinguishes reported vs provider-confirmed vs settled vs credited. | iDARMS reports its own provider callbacks as concessionaire reports only. |
| O10 | mTLS for the reporting client is required by the Framework but not found in CROIP. Credential issuance process per environment? | Security and onboarding. | OAuth client credentials now. Design the HTTP client so mTLS can be added without code change. |
| O11 | Is central messaging mandatory, or may iDARMS keep an audited local fallback gateway? | Messaging architecture. | Central first. Local fallback only after approval. |
| O12 | Local port collisions. CROIP uses 3001-3008, **3010, 3020, 3030** (governance, property, ratepayer), portal **3050**, a portal proxy on **4000**, ZITADEL **8080**, Mailpit **8025**. | O13 | Control-total cadence, sequence markers and who declares gaps. | Completeness evidence. | Daily per currency and event family. |
| O14 | Refund approvals, bank-detail changes and any fund movement. | Framework §1 requires a separately approved mandate. | Report refund events. Do not initiate fund movement. |
| O15 | Who authenticates ratepayers in iDARMS-facing apps? | O16 | Must CROIP validate that `propertyId` and `ratepayerId` on an incoming bill exist, belong to our assemblies, and match each other? | O26 | **Where does the registration call to CROIP live?** ADR-0001 §2 says the command goes "directly to CROIP's API", and the code does that from the portal's Next.js server actions (`apps/idarms-portal/src/lib/croip.ts`), so the portal holds the CROIP secret. `CLAUDE.md` §3A and `04` §4 say iDARMS UI → iDARMS API → CROIP through a `croip-adapter` with `pending_registrations`. | O27 | `concessions-management-service` (uncommitted) creates and edits concessions, assemblies, assignments and property type/usage lookups locally, and provisions one ZITADEL org per assembly.
